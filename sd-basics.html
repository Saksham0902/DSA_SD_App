The idea you'll own

Three reflexes from this topic

    1

    The interview

    A 45-minute HLD round has a shape. Follow it and you'll never freeze at a blank whiteboard.

    The framework (say the steps out loud)

    1. Requirements (5 min). Functional: the 3–4 features that matter. Non-functional: scale, latency, availability vs consistency, read/write ratio.
    2. Estimates (3 min). Users → requests per second → storage per year → bandwidth. Rough is fine; the point is to find the bottleneck.
    3. API (3 min). The 3–5 endpoints with inputs and outputs.
    4. Data model (5 min). Entities, keys, and which database fits the access pattern.
    5. High-level design (10 min). Client → load balancer → services → cache → database → queues. Walk one request through it.
    6. Deep dive (15 min). The one or two hard parts: hot keys, fan-out, consistency, failure. This is where SDE-2 is judged.

    Back-of-the-envelope, the only numbers you need

    1 day ≈ 86,400 s ≈ 105 s. So 1 million requests a day ≈ 12 per second. 100M DAU × 10 requests = 109/day ≈ 12k QPS average; peak is 2–3× that.

    Storage: records per day × size × 365 × years. Latency ladder: memory ~100 ns, SSD read ~100 µs, same-datacenter round trip ~0.5 ms, disk seek ~10 ms, cross-continent ~150 ms. One Postgres box handles a few thousand simple writes per second; Redis ~100k ops/s.

    2

    Scale

    From one server to millions of users, one bottleneck at a time.

    Vertical vs horizontal

    Scale up (vertical)

    • Bigger machine
    • No code changes
    • Hard ceiling, single point of failure

    Scale out (horizontal)

    • More machines behind a load balancer
    • Needs stateless app servers
    • Near-linear growth, survives failures

    The key move is making app servers stateless: sessions go to Redis or a signed token, files go to object storage. Then any server can handle any request, and you add servers freely. Step through the first lab tab.

    L4 vs L7, and the API gateway

    An L4 load balancer routes by IP and port: fast, protocol-agnostic. An L7 load balancer reads HTTP: it can route /api/orders to one pool and /images to another, terminate TLS, and set cookies.

    An API gateway is an L7 front door for microservices that also does the cross-cutting chores: authentication, rate limiting, request routing, aggregation, logging. Think of it as a Facade plus a Chain of Responsibility at the network edge.

    3

    Talking to clients

    Designing APIs people can't misuse, and pushing updates in real time.

    API design checklist

    1. Resources as nouns: POST /orders, GET /orders/{id}. Verbs are HTTP methods.
    2. Status codes that mean something: 201 created, 400 bad input, 401/403 auth, 404, 409 conflict, 429 too many requests, 5xx server.
    3. Cursor pagination for feeds: ?after=<last_id>&limit=20. Offset pagination gets slow and skips items when new rows arrive.
    4. Idempotency keys on writes that cost money: the client sends Idempotency-Key; retries return the stored result.
    5. Versioning: /v1/ in the path or a header; never break existing clients.

    REST for public CRUD APIs, gRPC for fast internal service-to-service calls, GraphQL when many clients need different shapes of the same data.

    Real-time: four ways to get news to the client

    Short polling: ask every few seconds. Simple, wasteful. Long polling: ask, and the server holds the request until there's news. Server-Sent Events: one long HTTP response the server keeps writing to; one-way, auto-reconnect. WebSockets: a full-duplex connection; both sides send any time. Chat and multiplayer need WebSockets; live scores and notifications are fine with SSE.
