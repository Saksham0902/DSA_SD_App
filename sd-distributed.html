The idea you'll own

Three reflexes from this topic

    1

    Speed

    Caches, CDNs and blob storage: serve bytes from as close and as cheap as possible.

    Caching strategies

    1. Cache-aside (lazy): read cache → on miss read DB → put in cache with TTL. On write, update DB then delete the key. The default.
    2. Read-through: the cache library loads from the DB itself on a miss. Same idea, less app code.
    3. Write-through: write cache and DB together. Always fresh, slower writes.
    4. Write-back (write-behind): write cache now, DB later in batches. Fast, can lose data if the cache dies.

    Eviction when full: LRU (least recently used) is the default; LFU for skewed popularity; TTL for freshness.

    CDN and object storage

    Large files (images, video, uploads) go to object storage (S3/GCS), never the database; the DB stores only the key. Clients upload directly to S3 with a pre-signed URL, so your servers never proxy gigabytes. A CDN caches those files (and static JS/CSS) at edge locations near users: lower latency, and most traffic never reaches you.

    2

    Async & consistency

    Queues, Kafka, and keeping data correct across services without distributed transactions.

    Queues and Kafka

    A message queue (SQS, RabbitMQ) hands each job to one worker and deletes it when acknowledged: great for background work. Kafka is a durable, replayable log: a topic is split into partitions, each an ordered append-only file. Messages with the same key go to the same partition, so they stay in order. A consumer group splits partitions among its members; each group gets every message, so email and analytics can read the same topic independently.

    Delivery is usually at-least-once: after a crash a message may come again. So consumers must be idempotent (dedupe by message ID).

    Sagas, outbox, CQRS

    Each microservice owns its database, so "place order" can't be one ACID transaction across Order, Payment and Inventory. A saga runs local transactions step by step; if one fails, earlier steps are undone by compensating actions (refund, release stock). Orchestrated sagas have a coordinator; choreographed ones react to each other's events.

    The outbox pattern fixes the dual-write bug (DB commit succeeds, Kafka publish fails): write the event into an outbox table in the same transaction, and a relay publishes it. CQRS separates the write model from read models that are built from events and shaped for queries.

    CAP and consistency models

    During a network partition, a distributed store must choose: refuse some requests to stay consistent (CP: banking, inventory counts, leader election) or answer with possibly stale data to stay available (AP: likes, feeds, shopping carts). Without a partition, the trade-off is latency vs consistency (PACELC).

    Models from strong to weak: linearizable (reads see the latest write), read-your-writes, monotonic reads, eventual (replicas converge if writes stop).

    3

    Staying up

    Failure handling, clever data structures, uptime maths, observability and security.

    Resilience: timeouts, retries, breakers, bulkheads

    Every network call gets a timeout. Retry only idempotent calls, with exponential backoff and jitter so clients don't retry in lockstep. A circuit breaker stops calling a failing dependency for a while (OPEN), then lets a few trial calls through (HALF-OPEN) before closing again. Bulkheads give each dependency its own thread pool so one slow service can't starve the rest. Always have a fallback: cached data, a default, or a friendly error.

    The algorithm toolbox

    1. Bloom filter: "definitely not present" or "probably present" in a few bits per item. Skip DB lookups for usernames, URLs already crawled.
    2. Geohash / quadtree: encode lat/long into a string whose prefix means "same area". Nearby search becomes a prefix query.
    3. HyperLogLog: count unique visitors in ~12 KB with ~1% error.
    4. Count-min sketch: approximate top-K / heavy hitters (trending hashtags).
    5. Token bucket / sliding window: rate limiting (see the HLD topic).
    6. Snowflake IDs: 64-bit, time-sortable unique IDs without a central counter.

    Availability, observability, security

    Nines: 99.9% allows ~8.8 hours of downtime a year; 99.99% allows ~53 minutes. Serial dependencies multiply (two 99.9% services in series ≈ 99.8%); redundancy in parallel raises it. Observability: metrics (RED: rate, errors, duration), structured logs with a trace ID, distributed tracing, and alerts on SLOs.

    Auth: authentication (who you are) vs authorisation (what you may do). JWT: a signed token any service can verify without a DB call; keep it short-lived with a refresh token. OAuth 2.0: delegated access ("log in with Google"). Hash passwords with bcrypt/argon2, use TLS everywhere, and rate-limit login.
