Three reflexes from this topic

    1

    The framework

    One answer shape for every HLD question. Every problem on this page is built with it, box by box.

    Every design is the same six moves

    1. Requirements: 3–4 core features + scale, latency, consistency.
    2. Numbers: reads/s and writes/s separately, storage, bandwidth. They decide the design.
    3. API: 3–5 endpoints.
    4. Data: entities, keys, and the store that fits the access pattern.
    5. Architecture: walk one write and one read through LB → services → cache → DB → queue. Add a box only to fix a problem you can name.
    6. Deep dive: the one thing that makes this system hard.

    In every lab below, the tag on each step tells you which move you're on: 📋 requirements, 🔢 numbers, 🔌 API, 🗄️ data, 🔧 architecture, 🔍 deep dive, 📈 scale.

    Worked example: URL shortener

    ShapeTiny records, read 100× more than written.
    SoCache in front of a key-value store; the write path is easy.
    Hard partGenerating unique 7-character codes without collisions or a bottleneck.
    2

    Read-heavy systems

    When reads dwarf writes, do the work at write time so reads are a lookup.

    Twitter / Instagram feed

    ShapeMillions post, everyone scrolls. Reads ≫ writes, and a feed must load in ~200 ms.
    SoPrecompute each user's timeline when a post is made (fan-out on write).
    Hard partCelebrities: one post × 50M followers. Fan-out on read for them.

    Autocomplete

    ShapeEvery keystroke is a query; answers must arrive in ~50 ms.
    SoNever rank at request time. Precompute the top suggestions per prefix offline; serve from memory.
    Hard partKeeping the precomputed lists fresh (trending queries) without slowing reads.
    3

    Real-time & maps

    Persistent connections, and things that move.

    WhatsApp

    ShapeBillions of messages, delivered instantly, with ticks; users are often offline.
    SoWebSocket servers keep connections; a store-and-forward message log.
    Hard partThe receiver is connected to a different server. How does the message find it?

    Uber

    ShapeA million drivers send their location every few seconds; riders want the nearest one now.
    SoLocations live in an in-memory geo index, not the main database.
    Hard partMatching: find nearby drivers fast and never give one driver two rides.

    Zomato / food delivery

    ShapeSearch nearby restaurants, place an order, a restaurant accepts, a rider delivers, the user tracks it.
    SoAn order state machine (the State pattern, stored in a DB row) driving events to everyone else.
    Hard partKeeping payment, restaurant and rider consistent when one of them fails (saga).
    4

    Correctness first

    Systems where doing something twice, or not at all, is the bug.

    Rate limiter

    ShapeEvery request to every API checks a per-user counter.
    SoA token bucket per key in Redis, checked at the gateway.
    Hard partMany gateway servers share one counter: the update must be atomic.

    Notification system

    ShapeMany services send email, SMS and push; providers are slow and flaky.
    SoAccept fast (202), queue per channel, workers deliver with retries.
    Hard partNever send twice, never lose one, respect user preferences and provider limits.

    Airbnb / hotel booking

    ShapeSearch is huge and can be slightly stale; booking is small and must be exact.
    SoSplit them: a search index for browsing, a relational DB for availability.
    Hard partTwo guests booking overlapping dates: hold every night atomically.
    5

    Files & media

    Big bytes never go through your application servers.

    YouTube

    ShapeHundreds of hours uploaded per minute; billions of views; every device needs a different quality.
    SoUpload straight to object storage, transcode with a queue of workers, serve from a CDN.
    Hard partTranscoding at scale and adaptive bitrate playback.

    Dropbox

    ShapeFiles change a little at a time and must appear on every device.
    SoSplit files into chunks addressed by hash; upload only the chunks that changed.
    Hard partSync and conflicts: two devices editing the same file.
