Recursion is delegation

You're in a dark cinema and want to know your row number. You can't see, so you tap the person in front: “Which row are you in?” They don't know either, so they tap the person in front of them. This repeats until someone in row 1 says “1”. Then answers travel back: 1, 2, 3… each person adds one and passes it on.

Nobody solved the whole problem. Each person did one tiny step and trusted the next person. That is recursion.

The three questions

Every recursive function is the answer to three questions. Ask them in this order:

  1. What's the smallest input I can answer instantly?That's the base case. Without it, the questions never stop.
  2. If a smaller version were already solved, what would I ask it?That's the recursive call. It has to move toward the base case.
  3. How do I turn its answer into mine?That's the combine step.

Here are the answers for factorial:

Base
n ≤ 1 → the answer is 1
Ask
fact(n - 1)
Combine
n * that answer

Notice what's missing: tracing every call in your head. Don't. Assume the smaller call returns the right answer and only check one level. This is the leap of faith, and it's the whole trick.

Going down, you're asking. Coming back up, you're answering.

Two calls make a tree

When a function calls itself twice, the calls branch. fib(n) asks fib(n - 1) and fib(n - 2), and each of those asks two more. Look at the tree below and you'll spot the same question asked again and again. That's wasted work.

Memoization fixes it: write each answer down the first time, and next time just read it. Flip the switch and watch whole subtrees disappear.

Where recursion bites

  • No base case, or one you never reach. Calls pile up until Python raises RecursionError. CPython's default limit is about 1000 frames.
  • Not shrinking. f(n) must call something closer to the base case, like f(n - 1) or f(node.left), never f(n) again.
  • Very deep inputs. A skewed tree or long linked list with 105 nodes will overflow. Use an explicit stack, or raise the limit with sys.setrecursionlimit carefully.
  • Mutable default arguments. def f(x, seen=[]) shares one list across every call, forever. Default to None and create the list inside.

Warm-ups interviewers still ask

Pure recursion, no trees yet. Each one is the three questions and a leap of faith. If any of these feel hard, it's the leap of faith that needs practice, not the problem.

Trees are recursion you can see

Every node is the root of a smaller tree. Learn the three visits, the two directions, then the problems interviewers love.

Every node is a tiny root

A binary tree is either empty, or a node with a left tree and a right tree. The definition is recursive, so the solutions are too. Almost every tree problem fits this shape:

Your only jobs: decide what an empty tree returns, and how to combine left, right and the node itself. The recursion handles the rest.

Each node is passed three times

Walk around the tree hugging its outline, starting on the left of the root. You pass every node three times: on its left side before going down, underneath between its two subtrees, and on its right side after both.

Do the work on the first pass and you get preorder. Second pass: inorder. Third: postorder. It's the same walk every time; you only choose when to speak. Tap a button to number the passes.

Output: tap a traversal

Information flows two ways

↑ Bottom-up

Return values

Children report up, the parent combines. Use it when a node's answer depends on its subtrees: height, diameter, balanced, max path sum. This is the postorder shape.

↓ Top-down

Parameters

The parent hands something down: a running sum, an allowed range, the current depth. Use it when a node needs to know about its ancestors: path sum, validate BST. This is the preorder shape.

The hybrid shows up constantly in interviews: return what the parent needs, but update a best-so-far variable on the side. Diameter and max path sum both work this way. You'll see it in the problems below.

Reshaping a tree without losing it

Flattening, deleting and rebuilding all share one danger: overwrite a pointer before you've used it and that part of the tree is gone. The cleanest fix is to only rewire nodes whose subtrees are already finished. Watch Flatten (114) do exactly that.

Choose, explore, un-choose

Backtracking is a depth-first walk over a tree of decisions. One template, four questions, two tricks, and every backtracking problem starts to look the same.

A maze with a breadcrumb trail

At each fork in a maze, you pick a path and keep walking. Dead end? Walk back to the last fork and try the next path. You never draw the whole maze; you just explore it one decision at a time.

In code, “walking back” means undoing your last choice, so the next option starts from exactly the state you had before. That undo is the only new idea compared to normal recursion.

Four questions before you code

  1. State: what am I carrying?Usually a path list plus an index, a remaining sum, or a used array.
  2. Choices: what can I do next from here?This becomes your for loop.
  3. Goal: when do I record an answer?At every node (subsets), only at full length (permutations), or when a target hits zero.
  4. Prune: when can I stop early?Sum too big, string invalid, square attacked. Good pruning is what makes backtracking fast.

There's only one path list, shared by every branch. Un-choose so your sibling starts clean.

Start index or used[]?

Order doesn't matter ({1, 2} is the same as {2, 1}): subsets, combinations, combination sum. Pass a start index and only look forward. That alone stops you from building the same set in a different order.

Order matters ([1, 2] differs from [2, 1]): permutations. Any position can take any unused element, so loop from 0 and track used.

Can an element be reused? Recurse with i. Each element at most once? Recurse with i + 1.

Killing duplicates

Input has repeats, like [1, 2, 2]? The two 2s would grow identical subtrees and give you duplicate answers. Fix: sort, then skip a value if it equals the one right before it at the same level:

“Same level” is the key phrase. Siblings with the same value are duplicates, so skip the twin. But going deeper, picking the second 2 right after the first is fine; that's how you get [2, 2]. Run Subsets II in the explorer above to see the skipped branch in red.

Grids: mark, explore, unmark

On a grid, your “path” is the set of cells you're standing on. Mark a cell before exploring its four neighbours so you don't walk in circles. Unmark it on the way out so a different path can use it later. Same choose / explore / un-choose rhythm, just on a board.

Counting the cost

Time and space for any recursive function, by drawing the tree and adding up its levels. No formulas to memorise.

Three questions price any recursion

  1. How many calls does one call make, and on what size? fib(n-1) + fib(n-2) → 2 calls, each about n − 1. search(mid+1, hi) → 1 call on half.
  2. How much work happens inside one call, not counting the calls? A comparison is O(1). A loop over the input, slicing a[:mid] or copying path[:] is O(n).
  3. Draw the tree, add it up level by level. Level total = (calls on that level) × (work per call). Time = sum of all levels. Space = how deep the tree goes (that's the most frames alive at once), plus any extra lists you keep.
time = Σ levels (calls × work per call) space = max depth × frame + extra

Watch the levels add up

Each tab below draws the call tree one level at a time. Boxes are calls (labelled with their input), the right column is that level's work. Watch which level is biggest: that's the whole story.

Space: the deepest point, not the total

fib(30) makes 2.7 million calls, but never more than 30 are alive at once. When a call returns, its frame is popped and the memory is reused. So stack space = the height of the tree, not its size. Then add anything you build on the side: a memo dict of n entries is O(n), the path list in backtracking is O(n), and the output list is usually counted separately.

The decoder

Read the problem, spot the phrase, reach for the template. Then prove it with the final round.

If the problem says…

“all subsets”, “power set”
Start index, record at every node. backtrack(i + 1)
“all arrangements”, “orderings”
used[], loop from 0, record at full length.
“choose k”, “sum to target”
Start index. Once each: i + 1. Unlimited: i. Sort and break when too big.
“may contain duplicates”, “unique results”
Sort, then if i > start and a[i] == a[i-1]: continue
“partition the string”
Start index over cut positions: try every end, recurse from it.
“in a grid”, “adjacent cells”
DFS 4 directions. Mark cell, explore, unmark.
“place so none conflict”, “fill the board”
Row by row with sets for O(1) is_valid. Return True to stop at the first solution.
Tree: needs info from children
Bottom-up. Return a value, combine in postorder.
Tree: needs info from ancestors
Top-down. Pass it as a parameter, preorder style.
