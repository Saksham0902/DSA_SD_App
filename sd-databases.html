Three reflexes from this topic

    1

    Choosing

    Pick the store from the access pattern, not from fashion.

    The database zoo, by access pattern

    1. Relational (Postgres, MySQL): tables, joins, transactions. Default for money, orders, users, anything with relationships and invariants.
    2. Key-value (Redis, DynamoDB): get/put by key, extremely fast. Sessions, caches, URL codes, carts.
    3. Document (MongoDB): JSON documents with flexible fields, fetched whole. Product catalogs, profiles, CMS content.
    4. Wide-column (Cassandra, HBase): huge write throughput, rows partitioned by key and sorted by a clustering column. Chat messages, time series, activity feeds.
    5. Search (Elasticsearch): inverted index for full-text and filters. Product search, logs.
    6. Graph (Neo4j): relationships are the data. Friend-of-friend, recommendations, fraud rings.
    7. Object storage (S3) + time-series (InfluxDB) + column analytics (BigQuery, ClickHouse) for blobs, metrics and reporting.

    SQL vs NoSQL, the honest version

    SQL

    • Schema, joins, ACID transactions
    • Flexible queries you didn't plan for
    • Scales reads with replicas; writes need sharding work

    NoSQL

    • Designed around known queries (model per access pattern)
    • Horizontal scale built in
    • Joins and multi-item transactions limited or absent

    Say it as a trade-off: "Orders need transactions and ad-hoc reporting, so Postgres. Chat messages are append-heavy, read by conversation and time, and huge, so Cassandra."

    2

    Indexes & ACID

    Make reads fast without scanning; make writes safe when several happen at once.

    An index is a sorted copy you can binary-search

    Without an index, WHERE email = ? reads every row: O(n). A B-tree index keeps the column sorted in a shallow tree of pages, so the lookup touches 3–4 pages even for a billion rows: O(log n). The cost: every insert and update must also update the index, and it takes disk.

    A composite index on (user_id, created_at) is sorted by user first, then time. It serves WHERE user_id = ? and WHERE user_id = ? ORDER BY created_at, but not WHERE created_at > ? alone: the leftmost-prefix rule.

    ACID, and the isolation levels behind the I

    Atomic: all or nothing. Consistent: constraints hold before and after. Isolated: concurrent transactions don't see each other's half-done work. Durable: committed means it survives a crash (write-ahead log).

    Isolation has levels, each preventing one more anomaly: Read Uncommitted (allows dirty reads) → Read Committed (Postgres default; allows non-repeatable reads) → Repeatable Read (MySQL InnoDB default; mostly stops phantoms there) → Serializable (as if one at a time; slowest). The lost update in the lab's last tab happens at Read Committed if you read-then-write in application code.

    3

    Scaling data

    Copies for reads and safety, splits for writes and size.

    Replication: copies of the same data

    A primary takes writes and streams changes to replicas that serve reads. Async replication is fast but replicas lag, so a user may not see their own just-written comment: route that user's reads to the primary for a few seconds (read-your-writes). Sync replication waits for a replica to confirm: no data loss on failover, slower writes. Leaderless systems (Cassandra, Dynamo) write to N nodes and use quorums: W + R > N means reads see the latest write.

    Sharding: split the data across machines

    When one primary can't take the writes or hold the data, partition rows by a shard key. A good key has high cardinality, spreads load evenly, and keeps the data a query needs on one shard (user_id for a user's orders). Bad keys create hot shards (country = India) or force scatter-gather queries across every shard.

    How do you map keys to shards? hash(key) % N is simple, but changing N moves almost every key. Consistent hashing puts servers and keys on a ring; a key belongs to the next server clockwise, so adding a server only moves the keys in one arc. Watch both in the lab.
