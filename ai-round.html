How you're scored

Google's document names three skills: prompt engineering, output validation and debugging. The other rows are what interviewers listen for in any code-reading round, from candidate reports and Meta's published rubric.

Code comprehension

Strong signalBuilds an accurate picture of the code before changing it. Reads the tests to learn the spec, names the data flow and invariants, and explains what a function does in plain words.
Weak signalEdits before understanding, asks the AI to "explain the whole repo", or can't say what a function is for.

Prompt engineering

Named by Google
Strong signalNarrow, context-rich asks: the exact code, the failing test, the rules. Asks for an explanation before code, a minimal diff, or edge cases, then iterates.
Weak signal"Fix all the bugs", "rewrite this file", or letting the assistant pick the approach.

Output validation

Named by Google
Strong signalReads every line, runs the whole suite, checks edge cases and the exact spec, confirms APIs exist and behave as claimed, and rejects wrong suggestions with a reason.
Weak signalPaste and run. Trusts "this is O(n)" or "this is the standard way" without checking.

Debugging

Named by Google
Strong signalReproduce, hypothesise out loud, check cheaply, fix the root cause with the smallest change, add a regression test.
Weak signalShotgun edits, or making the test green by hiding the symptom (try/except, clearing a cache).

Optimisation

Strong signalFinds the bottleneck by reasoning about complexity, picks the right structure (index, heap, deque, memo), and measures.
Weak signalMicro-tweaks, guessing, or accepting a "faster" version without checking hidden linear work.

Communication & ownership

Strong signalNarrates decisions, can explain every line including the AI's, states trade-offs, and says what to test next.
Weak signalLong silences, or "the AI wrote that part".

The 60 minutes

A time budget based on candidate reports and Meta's three-phase round. Say what you're doing as you go: silence gives the interviewer nothing to score.

OrientDebugBuildOptimise
0–3minutes

Clarify

Ask what the assistant can see, whether you can run tests, the Python version, and what "done" means.

Say"Before I start: can the assistant see every file, and can I run the tests?"
3–10minutes

Orient

Read the task and the tests first, then the entry points and data model. Run the tests and read the failure. Say your mental model in two or three sentences.

Say"So quote() sums unit prices, which are cached per… SKU. That's interesting given the bug report."
Ask the assistant"In 5 bullets: what does pricing.py do and what calls it? No changes yet."
10–25minutes

Debug

Form a hypothesis, check it cheaply, fix the root cause minimally, rerun everything, add a regression test.

Say"My hypothesis: the cache key ignores currency. If so, INR then USD should fail, and it does."
Ask the assistant"Is my hypothesis consistent with this failing test? What else could cause it?"
25–45minutes

Build

Pin the spec (rounding, boundaries, ties), decide the design yourself, use the assistant for drafts and boilerplate, and review its code line by line before you run it.

Say"Money stays in integers so the round-down rule holds. I'll let the assistant draft it, then check the rounding."
Ask the assistant"Implement X with rules A, B, C. Show only the changed function and list the edge cases you considered."
45–55minutes

Optimise

Find where the time goes, name the complexity, change the structure, keep the behaviour identical, and measure.

Say"find() scans the whole catalog per line: n × m. A SKU index makes it n + m."
Ask the assistant"What is the time complexity of quote() in items and catalog size? Where is the bottleneck?"
55–60minutes

Wrap up

Summarise what you changed and why, which suggestions you rejected, the trade-offs, and what you'd test or improve next.

Say"Three changes: the cache key, integer money, and an index. I rejected resetting the cache because it hid the bug."

Reading code you didn't write

This is the core skill, and it doesn't need AI. Practise it on any open-source module: ten minutes cold, then explain it out loud.

  1. Read the task and tests firstTests are the spec. Note what they call and what they expect: names, rounding, boundaries, errors.
  2. Find the entry pointsWhich public functions do the tests call? Open those first, not the helpers.
  3. Map the data modelWhat are the main types and what do their fields mean, including units (ms or s, paise or rupees)?
  4. Trace one call end to endFollow one test input through every function it touches. Write the path down.
  5. Note invariants and assumptions"Events are sorted", "indegree counts distinct deps", "prices are integers". Bugs live where these break.
  6. Run the tests and read the failureThe message, the expected and actual values, and the line. It often points at the exact assumption.
  7. Say your mental modelTwo or three sentences out loud. This is what the interviewer is listening for.
  8. Only then ask the assistantWith a hypothesis and a narrow question, not "explain everything".

The debugging loop

If the rerun fails, go back to your hypothesis rather than piling on edits.

  1. Reproduce it: run the failing test
  2. Read the failure: expected vs actual
  3. Hypothesise out loud
  4. Check it cheaply: a print, a smaller input, or one narrow question
  5. Fix the root cause with the smallest change
  6. Rerun every test and add a regression test
  7. Explain the fix in one sentence

Prompts that score well

Narrow, specific asks that you can check. Each one shows the interviewer how you think, so use them on purpose, not as a crutch.

01Orient

Here are pricing.py and cache.py. In five bullets: what does this module do, what are its entry points, and what data flows between them? Don't suggest changes yet.

02Locate

test_quote_in_two_currencies fails: expected 699, got 49900. Which function is most likely responsible, and why? Quote the line.

03Check a hypothesis

I think the cache key ignores the currency (line 10). Is that consistent with this failure? What else could cause it?

04Minimal fix

Propose the smallest change that fixes this, as a diff. Don't refactor or rename anything else.

05Spec first

Before writing code, restate the rules for this feature in your own words, including rounding, boundaries and ties. I'll confirm them.

06Edge cases

List the edge cases this function doesn't handle, most likely first. One line each.

07Tests

Write three focused tests for slowest_endpoints(): a normal case, a tie, and k larger than the number of paths. Plain asserts.

08Complexity

What is the time complexity of first_alert() in terms of the number of events? Point to the line that makes it so.

09API check

Does Python's OrderedDict have move_to_front()? If not, what are the exact methods to mark an item most recent and to remove the oldest?

10Review my change

Here is my diff. Review it like a strict reviewer: correctness, edge cases, naming. Don't rewrite it, just list the issues.

11Explain an error

Explain this traceback in plain words and point to the first line in our code where it goes wrong.

12Keep it short

Answer in under 6 lines. Show code only for the function that changes.

Prompts that cost you points

  • "Fix all the bugs." It's unbounded and unverifiable, and the round is scored on how you narrow problems down.
  • "Rewrite this file to be cleaner." You inherit a big diff you must review under time pressure, and it can break callers.
  • Pasting the whole repo with no question. You get a summary you could have read yourself.
  • "What's the best approach?" before you have one. Decide, then ask for a check.
  • Arguing with the assistant. Run the code: the test settles it faster.

Python you'll be reading

Candidate reports mention Python codebases. These are the behaviours that make AI suggestions subtly wrong and that you need to spot on sight.

defaultdict(list)

Reading d[k] inserts k with a fresh default. Check with k in d or d.get(k) when you only want to look.

Counter.most_common(k)

The k largest counts. Equal counts keep the order they were first seen in, which is not alphabetical.

deque

O(1) append and pop at both ends. deque(maxlen=n) silently drops items from the other end. Indexing the middle is O(n).

OrderedDict

move_to_end(key) and popitem(last=False) give O(1) LRU bookkeeping. A plain dict keeps insertion order too, but has neither method.

heapq

A min-heap on a plain list. For a max-heap, push negatives. Tuples compare item by item, so ties fall through to the next item, and two items that can't be compared raise TypeError.

bisect_left / bisect_right

The insertion point before or after any equal values. The list must already be sorted.

sorted(xs, key=...)

Stable: equal keys keep their original order. key=lambda x: (-score, name) gives "highest first, then alphabetical".

round(x)

Rounds half to even: round(2.5) == 2 and round(0.125, 2) == 0.12. For money, use integers or Decimal.

// and %

Floor division rounds toward minus infinity: -7 // 2 == -4 and -7 % 2 == 1.

def f(x, acc=[])

The default list is created once and shared by every call. Use acc=None, then create the list inside.

[[0] * n] * m

m references to the same row, so writing one cell changes every row. Use [[0] * n for _ in range(m)].

@dataclass

Writes __init__, __repr__ and __eq__ for you. With frozen=True instances are hashable; otherwise __hash__ is None and they can't go in a set.

Generators

A generator can be consumed once. A second sum() over the same one returns 0.

Recursion depth

The default limit is about 1,000 frames, so a recursive DFS on a long chain raises RecursionError. Use an explicit stack.

is vs ==

is compares identity. Use it only for None. Small ints and short strings are cached, which makes a wrong is look right in tests.

time.perf_counter()

Use it to measure durations. time.time() can jump when the system clock is adjusted.

AI mistakes to catch

Each card is a real kind of mistake assistants make. Read the code, decide what's wrong, then reveal.

Card 1 of 16
cache.move_to_front(key)
old = cache.popitem(first=True)

Hallucinated method

OrderedDict has no move_to_front(), and popitem takes last=, not first=.

How to catch itAsk for the exact signature, or run it. The real calls are move_to_end(key) and popitem(last=False).
Card 2 of 16
p95 = statistics.quantiles(xs, n=100)[94]

Real API, wrong meaning

quantiles interpolates between ranks. A nearest-rank spec needs the value at rank ceil(0.95·n).

How to catch itCompare against the spec and a tiny example: 1..20 should give 19, but this gives 19.95.
Card 3 of 16
def quote(self, items, currency):
    self.cache = PriceCache()   # avoid stale prices
    ...

Fixing the symptom

The test goes green, but caching is gone and the wrong cache key is still there.

How to catch itRun the whole suite. The cache-hit test fails. Ask "what caused the stale value?"
Card 4 of 16
subtotal = int(subtotal * 0.95)

Floats for money

12990 × 0.95 = 12340.5, and int() drops the half, so the discount is rounded the wrong way.

How to catch itIntegers only: subtotal - subtotal * pct // 100. Test a value that ends in .5.
Card 5 of 16
if end - window <= e.ts <= end:

Off-by-one at a boundary

An event exactly window seconds old counts when the spec says it shouldn't.

How to catch itWrite a test with an event exactly on the edge.
Card 6 of 16
heapq.nlargest(k, ((avg, path) for ...))

Wrong tie-break

On equal averages, the larger path name wins, but the spec wants the smaller one.

How to catch itTest ties explicitly. Use sorted(key=lambda x: (-avg, path)).
Card 7 of 16
start = min(finish[d] for d in deps)

min where it should be max

A task needs all of its dependencies done, so start is the max of their finish times.

How to catch itA diamond-shaped test catches it immediately.
Card 8 of 16
def refresh(self, token):
    if token in self._data: ...renew...

Revives what it shouldn't

It never checks expiry, so an expired session comes back to life: a security bug.

How to catch itTest the expired path. Reuse the existing expiry check instead of rewriting it.
Card 9 of 16
for e in events:
    if e.path in seen_list: ...

Hidden O(n) work

in on a list is a scan, so the "O(n)" loop is O(n²).

How to catch itLook for in-on-list, list.remove, slicing or sorting inside loops.
Card 10 of 16
try:
    price = lookup(sku)
except Exception:
    price = 0

Swallowed errors

Unknown SKUs silently become free.

How to catch itKeep the codebase's error contract and let callers see the failure.
Card 11 of 16
def add(item, bucket=[]):
    bucket.append(item)
    return bucket

Mutable default argument

The same list is shared across calls, so items leak between requests.

How to catch itUse bucket=None, then bucket = [] if bucket is None.
Card 12 of 16
from graphlib import TopologicalSorter
return list(TopologicalSorter(t).static_order())

Changing a contract quietly

The tie order and the exception type change, and unknown dependencies are accepted.

How to catch itCheck the tests that encode the contract: order, errors and inputs.
Card 13 of 16
if now_ms() - created > ttl_s:

Mixed units

Milliseconds compared with seconds, so sessions die after 30 ms.

How to catch itRead the names and docstrings. Convert one side explicitly (ttl_s * 1000).
Card 14 of 16
def test_quote():
    assert svc.quote(items, "INR")

Tests that can't fail

Any non-zero total passes, so the test checks almost nothing.

How to catch itAssert exact expected values and include a failing-path test.
Card 15 of 16
"I refactored PricingService into three classes and fixed the bug."

Big rewrite for a small bug

A huge diff to review, with changed names that break callers you can't see.

How to catch itAsk for the minimal diff. Reject unrequested refactors.
Card 16 of 16
def dfs(node):
    for child in graph[node]:
        dfs(child)

Recursion that blows up

A 20,000-node chain exceeds Python's recursion limit.

How to catch itUse an explicit stack or iterate in topological order.

    Open-ended problems

    For early-career candidates, one technical round becomes a vague problem you have to scope. The first two prompts come from candidate reports. Ask before you code.

    Line wrap

    “Given a string and an integer width, return how many lines it takes to write the string.”

    Questions to ask

    • Do we wrap at word boundaries, or anywhere?
    • What if a single word is longer than the width?
    • How do multiple spaces and newlines in the input count?
    • Can width be zero or negative?

    Edge cases

    • Empty string (0 or 1 lines?)
    • A word exactly the width
    • Trailing spaces
    • Unicode characters

    Approach

    Agree on rules first, then greedy: keep adding words while the line plus a space plus the next word fits; start a new line otherwise. O(n).

    What they watch: Whether you ask before you code. One candidate rushed and needed a hint; the interviewer said they cared more about the clarifying than the solution.
    snake_case to camelCase

    “Write a function that converts snake_case identifiers to camelCase.”

    Questions to ask

    • What about leading or trailing underscores?
    • Multiple underscores in a row?
    • Digits after an underscore?
    • Is the input already camelCase sometimes? Mixed case?

    Edge cases

    • "" and "_"
    • "__init__"
    • "user_id_2"
    • "HTTP_status"

    Approach

    Write the rules as a table of examples, confirm them, then split on "_" and handle empties per the agreed rules.

    What they watch: Scoping. A reported L4 screen spent its last 10 minutes on exactly this, and the edge cases mattered more than the code.
    Deduplicate customers

    “We have customer records from three systems. Remove duplicates.”

    Questions to ask

    • What makes two records the same person: email, phone, name and address?
    • Which record wins when fields conflict?
    • How many records, and how often do we run this?
    • Is it OK to merge wrongly sometimes?

    Edge cases

    • Email case and dots
    • Phone formats and country codes
    • Missing fields
    • Chains: A matches B, B matches C

    Approach

    Normalise keys (lowercase email, E.164 phone), group by key, union-find to merge chains, apply a field-precedence rule.

    What they watch: Whether you define "duplicate" before building, and notice transitive matches.
    Retry a flaky call

    “A network call fails sometimes. Write something that retries it.”

    Questions to ask

    • Which errors are retryable?
    • Is the call safe to repeat (idempotent)?
    • What is the total time budget?
    • How many attempts?

    Edge cases

    • Timeouts versus 4xx errors
    • Thundering herd
    • A call that succeeded but timed out

    Approach

    Exponential backoff with jitter, max attempts and an overall deadline, retrying only retryable errors, with idempotency keys for writes.

    What they watch: Safety thinking: idempotency and not hammering a struggling service.
    Paginate results

    “Add pagination to an endpoint that lists orders.”

    Questions to ask

    • Sorted by what?
    • Can rows be added or deleted while someone pages?
    • Page size limits?
    • Do clients need to jump to page N?

    Edge cases

    • Inserts between page requests
    • Ties in the sort key
    • Last page

    Approach

    Cursor-based pagination on (created_at, id) with a stable sort and a capped page size; offset only if page jumps are required.

    What they watch: Whether you notice offset pagination skips or repeats rows when data changes.
    Rate-limit a function

    “Limit how often a function can be called.”

    Questions to ask

    • Per user, per IP, or global?
    • Smooth rate, or bursts allowed?
    • One process or many servers?
    • What happens to rejected calls?

    Edge cases

    • Clock changes
    • Many servers
    • Burst at the window boundary

    Approach

    Token bucket per key: refill by elapsed time; in-process with a lock, or atomically in Redis across servers.

    What they watch: Picking an algorithm that fits the stated burst behaviour and explaining the multi-server version.
    Top errors from logs

    “Parse a log file and report the most common errors.”

    Questions to ask

    • What is the log format, and do malformed lines exist?
    • How big is the file?
    • Top by count, or by recent rate?
    • How are similar messages grouped?

    Edge cases

    • Multi-line stack traces
    • Huge files
    • Messages differing only by an id

    Approach

    Stream line by line, normalise messages (strip ids and numbers), count with a dict, then a heap for the top k. Memory O(distinct).

    What they watch: Streaming instead of loading everything, and normalising messages.
    Free meeting slots

    “Given two people's calendars, find times they could meet.”

    Questions to ask

    • Time zones?
    • Working hours?
    • Minimum meeting length?
    • Are calendars sorted? Do events overlap?

    Edge cases

    • Back-to-back meetings
    • All-day events
    • Overlapping events in one calendar

    Approach

    Merge each calendar's busy intervals, merge both, then take the gaps within working hours that are at least the minimum length.

    What they watch: Interval handling and asking about time zones up front.

    AI product integration

    Internal documents list “AI product integration” for most roles above entry level. Expect it in system design and in the project deep-dive: how you'd build a feature on top of a model, safely and cheaply.

    Calling a model

    Requests and responses, tokens, the context window, temperature, max output, streaming. Cost and latency grow with tokens.

    Prompts in production

    Templates with versioning, clear instructions, a few examples, and structured output (JSON with a schema) that you validate.

    Grounding (RAG)

    Chunk your documents, embed them, search a vector index, rerank, and put the top passages in the prompt with citations. Respect permissions at retrieval time.

    Tool use

    The model asks to call a function; your code validates the arguments and runs it. Least privilege, and confirmation for risky actions.

    Evaluation

    A labelled set of realistic cases scored on every prompt or model change: automatic checks, careful LLM-as-judge, human review, then online A/B tests.

    Reliability

    Timeouts, retries with backoff, rate limits and quotas, circuit breakers, and a fallback path that works without the model.

    Cost and latency

    Caching (exact or semantic), smaller models for easy requests, context trimming, batching, capped output and streaming UX.

    Safety

    Prompt injection from untrusted content, PII redaction, output filters, grounding to reduce made-up answers, and humans in the loop for consequential actions.

    Observability

    Log prompts and outputs (privacy-safe), track quality, cost and latency, collect user feedback, and watch for drift after model updates.

    Three designs to talk through

    Give yourself 15 minutes each: requirements, architecture, what fails, and what you'd measure.

    A help-centre assistant over your docs

    Requirements

    • Answers only from company docs, with citations
    • Hands off to a human when unsure
    • Respects who can see which docs

    Architecture

    • Ingestion: chunk docs, attach metadata and permissions, embed, refresh on update
    • Query: retrieve, filter by permission, rerank, answer only from the passages with citations
    • Guardrails, a human hand-off, caching of common questions

    What fails

    • Stale index or a doc the user may not see
    • Model ignores the passages and makes things up
    • Prompt injection inside documents

    What to measure

    • Answer accuracy on an evaluation set
    • Deflection and escalation rates
    • Latency p95 and cost per answer
    AI summaries on a customer timeline

    Requirements

    • Summarise the last 90 days of a customer's activity for an agent
    • Under 2 seconds, fresh data
    • No sensitive fields in prompts

    Architecture

    • Pre-aggregate events into a compact digest per customer
    • Generate on demand with a cached result keyed by (customer, last event id)
    • Redact PII before the prompt; template with a strict output schema

    What fails

    • Summaries that invent events
    • Cost spikes from busy customers
    • Stale cache after new activity

    What to measure

    • Agent satisfaction and edits to summaries
    • Hallucination rate on a labelled sample
    • Cache hit rate and cost per summary
    Reply suggestions for a support inbox

    Requirements

    • Suggest 3 replies for each new ticket for 10k agents
    • Learn from accepted replies
    • Never send without an agent

    Architecture

    • Async job on ticket arrival: retrieve similar resolved tickets, then generate suggestions
    • Store suggestions with the ticket; the UI shows them instantly
    • Feedback loop from accepted and edited replies into the evaluation set

    What fails

    • Wrong tone or wrong facts
    • Burst traffic during outages
    • Leaking another customer's data from similar tickets

    What to measure

    • Acceptance rate
    • Time to first response
    • Error reports and cost per ticket

    Questions people ask

    Is DSA dead?

    No. The regular coding rounds are still DSA without AI, and even the AI round needs DSA: you can't spot an O(n²) loop or a wrong heap tie-break without it. Keep one or two problems a day.

    Will my loop in India have this round?

    As of October 2026 there are no reports of the pilot outside the US. Ask your recruiter which format your loop uses, and prepare for both. The classic loop is the default.

    Can I use AI in the other rounds?

    No, only where the interviewer explicitly allows it. Google brought back in-person rounds partly because of AI misuse in remote interviews.

    Which language will it be?

    Not officially published. Candidate reports mention Python. Ask your recruiter, and be fluent at reading Python and your main language.

    What if Gemini gives me a wrong answer?

    That's the point. Catching it, saying why, and choosing a better path is the output-validation signal they score.

    Should I avoid the assistant to look strong?

    No. AI fluency is scored, so use it deliberately: narrow questions, drafts you review, API checks. Not using it at all gives them less to evaluate.

    How is it different from Meta's round?

    Google requires Gemini and frames the round as code comprehension (read, debug, optimise). Meta lets you pick models and leans on building a feature. Both test reading code, verifying AI output and narrating.

    Is there a no-AI code reading round too?

    Reportedly yes, around 45 minutes, for example reviewing broken code in a Google Doc. Practise reading and fixing code without the assistant as well.

    Does Google use AI on my interview?

    News sites report that Google is testing Gemini to transcribe interviews and take notes in Google Meet. Google hasn't said more about it publicly.
