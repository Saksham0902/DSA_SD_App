== sd-start.html lab-change
-- -
M: sd
P: A notification service gets three requests in a row: send email, then also SMS, then also WhatsApp. How do you shape the code so each new channel doesn't mean editing and re-testing the old code?
I: Find what changes (the channel), hide it behind an interface, and hand the implementations in from outside. After that, a new channel is one new class and nothing old is touched.
S: Boxes are classes; the arrows are UML relationships, explained as they appear.

S: (bad) a class that had to be edited again

== sd-basics.html lab-scale
-- grow
M: sd
P: An app grows from 100 users to 100 million. What breaks first at each stage, and what fixes it?
I: Each step fixes only the current bottleneck: separate database, stateless app servers behind a load balancer, cache and read replicas, CDN, queues, then sharding. That's how to narrate an HLD answer.
S: (cur o) the part just added
S: (on e) connections in use
S: (ok o) parts scaled out to several copies
S: (bad o) the bottleneck
S: {users}{bottleneck} the current scale, and what limits it

-- rr
M: sd
P: A load balancer sends requests to three servers. Round robin takes turns: request n goes to server n mod 3. What happens when some requests are much heavier than others?
E: most requests cost 1 unit of work; every third one is a heavy report costing 5.
I: Round robin is fair by count, not by work: all the heavy requests land on server A (15 units against 3 and 3).
S: Each bar is one server's work so far.
S: (cur) the server that just got a request
S: (bad) the busiest server
S: {request}{busiest} the request being placed, and the most loaded server

-- lc
M: sd
P: Same servers, same mix of requests, but now each request goes to the server with the least work in flight (least connections).
E: most requests cost 1 unit of work; every third one is a heavy report costing 5.
I: The load ends up far more even (7, 6 and 8) because the algorithm reacts to actual load instead of taking turns.
S: Each bar is one server's work so far.
S: (cur) the server that just got a request
S: {request}{busiest} the request being placed, and the most loaded server

== sd-databases.html lab-idx
-- scan
M: sd
P: Find every user in Pune when there's no index on the city column.
E: 12 rows stored in insert order; 3 of them are in Pune.
I: Without an index the database must read every row (a Seq Scan), even after it finds a match. 12 reads here; 1,000,000 reads on a million-row table, on every request.
S: (cur) the row being read
S: (ok) a match
S: (bad) a row read for nothing
S: {rows read}{matches} the cost against the useful result

-- btree
M: sd
P: How does an index find a row without scanning the table? Look up id = 70 in a B-tree, then see how a two-column index is ordered.
I: Each box is a disk page of sorted keys, so a lookup is a binary search spread over pages: 3 page reads instead of a table scan. A composite index (user_id, created_at) only helps queries that start with user_id.
S: (cur o) the page being read
S: (on o f) the path taken so far
S: (ok o) the matching entry
S: (bad o) a query the index can't help
S: {page reads}{rows scanned} the cost of the lookup

-- lost
M: sd
P: Two payments of ₹30 and ₹50 hit the same wallet holding ₹100 at the same moment. What balance ends up in the database?
I: Both transactions read 100 before either writes, so one debit overwrites the other: the user pays ₹80 but loses only ₹50. Fix it with an atomic `UPDATE … SET balance = balance − x`, or lock the row with `SELECT … FOR UPDATE`.
S: Two lanes, one per transaction; each column is a moment in time.
S: (cur) the step happening now
S: (on f) a read, or a lock being held
S: (ok) the correct result
S: (bad) the wrong result
S: {balance in DB}{expected} what the database holds, against what it should hold

== sd-databases.html lab-ring
-- mod
M: sd
P: Keys are spread over shards with `hash(key) % N`. What happens when a 4th shard is added?
I: Changing N changes almost every key's shard: 7 of 8 keys must move, and every cache keyed this way goes cold at once.
S: (cur) the shard count that changed
S: (ok) keys that stay where they are
S: (bad) keys that must move
S: {shards}{moved} the number of shards, and keys moved

-- ring
M: sd
P: Consistent hashing: servers and keys are hashed onto a ring, and each key belongs to the next server along. What moves when a server is added?
I: Only the keys on the new server's arc move. With a few points the arcs are uneven, so real systems give each server 100–200 virtual nodes around the ring.
S: The circle is the hash ring (0–360°); coloured labels are servers, small dots are keys.
S: {servers}{keys moved} servers on the ring, and keys moved by the last change

== sd-distributed.html lab-cache
-- aside
M: sd
P: Cache-aside: the app checks the cache before the database. What happens on a hit, on a miss, and when the price changes?
I: A miss loads from the database and fills the cache. On a write, update the database and then delete the cache key rather than overwrite it, so the next read reloads fresh data.
S: (cur o) the step happening now
S: (on o f) the services involved
S: (ok o) a cache hit, or the data that was kept
S: {result}{latency} where the answer came from, and how long it took
S: {cache contents} what the cache holds now

-- lru
M: sd
P: An LRU cache holds at most 3 items. When it's full, which item gets evicted?
E: put A, put B, put C, get A, put D
I: Every use moves an item to the most-recent end, so the least recently used item is evicted: B goes, and A survives because it was just used.
S: Left is least recently used, right is most recently used.
S: (cur) the item just touched
S: (ok) a hit
S: (bad) the evicted item
S: {capacity}{last op} the size limit, and the last operation

== sd-distributed.html lab-async
-- kafka
M: sd
P: Order events go into a Kafka topic with 3 partitions, read by a consumer group. Which consumer reads what, and what happens when one crashes?
I: Events with the same key always land in the same partition, so they stay in order. Each partition has one consumer in the group. A crash before committing the offset means the event is read again, so handlers must be idempotent.
S: (cur o) the event or consumer active now
S: (on o f) partitions and their assigned consumers
S: (bad o) the consumer that failed

-- saga
M: sd
P: Placing an order spans several services (order, payment, inventory), each with its own database, and there's no global transaction. What happens when a later step fails?
I: A saga runs one local transaction per service. When a step fails, compensating actions undo the earlier steps in reverse (refund, then cancel), so the system ends up consistent eventually.
S: (cur o) the step running now
S: (ok o) a committed step
S: (bad o) the step that failed
S: (on e) messages between services

-- outbox
M: sd
P: An order must be saved and an OrderPlaced event published to Kafka. Two writes to two systems: what if one of them fails?
I: Write the event into an outbox table in the same database transaction as the order. A relay publishes it afterwards and marks it sent. A crash can cause a duplicate publish but never a lost one, so consumers dedupe by event ID.
S: (cur o) the step happening now
S: (ok o) committed
S: (bad e) the write that can fail
S: (on e) the path the event takes

-- bloom
M: sd
P: A Bloom filter answers "have I seen this before?" using a small array of bits. It can say "definitely not" or "probably yes".
E: 12 bits and 3 hash functions; add "cat" and "dog", then ask about "emu" and "cow".
I: Any 0 bit proves an item was never added (emu). All 1 bits only mean "probably": cow was never added, but its bits were set by cat and dog. That's a false positive.
S: (cur) bits being set or checked now
S: (ok) a checked bit that is 1
S: (bad) a checked bit that is 0, which proves "never added"
S: {query}{answer} the question being asked, and the filter's answer

== sd-lld.html lab-race
-- bug
M: sd
P: Asha and Ben click the same free seat, A7, in the same millisecond. The code checks that the seat is free, then books it. What goes wrong?
I: Both threads pass the check before either writes, so both get a confirmation and the last write wins. Check-then-act is a race whenever the check and the write aren't one atomic step.
S: Two lanes, one per user's thread; each column is a moment in time.
S: (cur) the step running now
S: (ok) a booking that succeeded
S: (bad) the double booking
S: {seat A7}{owner} the seat's status, and who the database says owns it

-- cas
M: sd
P: The same race, fixed inside one server: both threads call `putIfAbsent` (an atomic compare-and-set) on the seat map.
I: Exactly one thread wins and the other is rejected. But this only works inside one JVM; with 10 app servers, each has its own map.
S: Two lanes, one per user's thread; each column is a moment in time.
S: (cur) the step running now
S: (ok) the booking that won
S: (bad) the request that was rejected
S: {seat A7}{owner} the seat's status, and its owner

-- db
M: sd
P: The same race across many app servers: both send a conditional `UPDATE … WHERE status = 'FREE'` to the database.
I: The database applies the updates one at a time, so only the first changes a row; the second updates 0 rows and is rejected. The database is the referee.
S: Two lanes, one per app server; each column is a moment in time.
S: (cur) the step running now
S: (ok) the booking that won
S: (bad) the request that was rejected
S: {seat A7}{owner} the seat's status, and its owner
