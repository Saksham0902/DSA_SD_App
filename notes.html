Arrays & Hashing

Open topic →

Trade memory for time: remember what you've seen in a dict/set so the inner loop becomes an O(1) lookup.

Must know

  • Seen before? → set: check, then add, in one pass.
  • Pair to a target → dict value → index; look up target − x before storing x.
  • Group things that are 'the same' → a canonical key: sorted string or a 26-count tuple.
  • Count things → Counter; top-k by frequency → bucket by count (O(n)) or a heap.
  • Range sums → prefix sums: sum(l..r) = pre[r+1] − pre[l].
  • Subarray sums to k (negatives allowed) → prefix sum + dict of how often each prefix appeared; start with {0: 1}.
  • Values in 1..n → the array is its own hash: mark index x − 1 (negate / swap into place).

Template

The template you'll own

1seen = {} # remember what you've passed
2for i, x in enumerate(nums):
3 if target - x in seen: # ask before you store
4 return [seen[target - x], i]
5 seen[x] = i

Traps

  • Lists can't be dict keys; use a tuple.
  • Store the index after the lookup, or x pairs with itself.
  • Dict/set ops are O(1) average; say so.
  • Matrix in place: record which rows/cols to clear first, then clear.

If you see… → do

“Contains duplicate”, “have we seen this before?”, “first repeated”

A set. Check, then add. One pass.

Two numbers that combine to a target (sum, difference)

Dict value → index. For each x, look up target − x before storing x.

Group things that are “the same” after rearranging (anagrams, shifted strings)

Dict keyed by a canonical form: sorted string, or a tuple of 26 counts.

Frequencies: “most common”, “top k frequent”, “is it an anagram”

Counter. For top k without sorting, bucket by frequency (index = count).

Longest consecutive run in an unsorted array, in O(n)

Put everything in a set. Only start counting at x where x − 1 is missing.

Many “sum of range” queries on a fixed array

Prefix array with a leading 0: sum(l..r) = pre[r+1] − pre[l].

Count subarrays whose sum is k (negatives allowed)

Running sum + dict of prefix counts seeded {0: 1}. Add seen[running − k] each step.

Each answer depends on everything to its left and right (product except self, trapping water)

Two passes: left-to-right with a running value, then right-to-left.

O(1) extra space and values in the range 1…n

Use the array as its own hash: mark value v by flipping the sign at index v − 1.

Rotate a square matrix 90° clockwise in place

Transpose, then reverse each row.

Walk a matrix in a spiral

Four walls: top, bottom, left, right. Walk one edge, move that wall in, repeat while they haven’t crossed.

Mark rows / columns of a matrix with O(1) extra space

Store the flags in row 0 and column 0. Keep two booleans for whether they had zeros themselves.

An inner loop that searches the input for a partner or a duplicate

Replace it with a set/dict lookup: O(n²) → O(n) time, at the price of O(n) space.

“What’s the space complexity?” for a hashing solution

Count what the dict can hold: up to n keys → O(n). A fixed 26-letter count array → O(1).

Building a key for each item (sorted string, tuple, serialised path)

Multiply: n items × cost of one key. Sorted key O(n·k log k), count key O(n·k).

DSA · 02

Two Pointers

Open topic →

Two indexes move toward each other (sorted input) or in the same direction (reader/writer) so you never need a nested loop.

Must know

  • Sorted + pair/triple to a target → L and R at the ends: sum too small → L++, too big → R−−.
  • 3Sum → sort, fix i, two-pointer the rest; skip equal neighbours to avoid duplicates.
  • Container / trapping water → move the shorter side; it's the bottleneck.
  • Remove / compact in place → writer w and reader r; copy kept values to w.
  • Three-way partition (sort colors) → low / mid / high pointers (Dutch flag).
  • Merge two sorted arrays in place → fill from the back.
  • Palindrome checks → compare from both ends; 'delete one char' → try skipping either side once.

Template

The template you'll own

1l, r = 0, len(nums) - 1
2while l < r:
3 s = nums[l] + nums[r]
4 if s == target:
5 return [l, r]
6 if s < target:
7 l += 1 # need bigger
8 else:
9 r -= 1 # need smaller

Traps

  • Two pointers needs sorted input (or a monotonic reason to move).
  • Dedup in 3Sum: skip after a match, not before.
  • Sorting costs O(n log n); say it.
  • Off-by-one: while l < r, not <=, for pairs.

If you see… → do

Sorted array + find a pair with a target sum

l at the start, r at the end. Too small → l += 1. Too big → r −= 1.

Max area / water between two lines chosen from an array

Start widest. Always move the shorter wall inward.

3Sum, 4Sum, “triplets that sum to …”

Sort. Fix the first number(s) in a loop, two-pointer the rest. Skip equal neighbours to kill duplicates.

Palindrome check (maybe ignoring symbols, maybe one deletion allowed)

Pointers at both ends, move inward comparing. On a mismatch with one deletion allowed, try skipping either side once.

Trapping rain water

Two pointers with lmax and rmax. Process whichever side has the lower bar.

“In place”: remove, dedupe, compact, move zeroes

Writer w and reader r. Copy to w only when the reader finds something worth keeping.

Partition into three groups (0/1/2, low/mid/high) in one pass

lo, i, hi. 0 → swap to lo, advance both. 2 → swap to hi, shrink hi, don’t advance i. 1 → advance i.

Merge into an array that has empty space at the end

Fill from the back: compare the largest remaining of each, write at the end.

Is s a subsequence of t? Compare two sequences in order

One pointer per sequence. Advance the s pointer only on a match; always advance t.

Cycle in a linked list or in repeated function application (happy number, duplicate number 287)

Fast and slow pointers. Fast moves 2, slow moves 1. If they meet, there’s a cycle.

A while loop with two pointers moving towards each other (or both forward)

Count total moves: each pointer travels at most n → O(n), not O(n²).

“Sort the array first, then two pointers”

Say O(n log n) for the sort, O(n) for the scan → O(n log n) overall; space O(1) or O(n) depending on the sort.

k-Sum with two pointers inside k − 2 loops

O(n^(k−1)): 3Sum O(n²), 4Sum O(n³).

DSA · 03

Sliding Window

Open topic →

A contiguous range that grows on the right and shrinks on the left, updating a running summary instead of recomputing.

Must know

  • Fixed size k → add the new item, drop the item k back.
  • Longest valid → expand R every step; while invalid, shrink L; record after fixing.
  • Shortest valid → expand R; while valid, record and shrink L.
  • Window state: a Counter, a set, a 'need/have' pair, or a running sum.
  • Replace up to k chars → window is valid while len − maxCount ≤ k.
  • Exactly k distinct → atMost(k) − atMost(k − 1).
  • Max of every window → monotonic deque of indexes (decreasing values).

Template

The template you'll own

1l = 0
2for r, x in enumerate(nums):
3 add(x) # expand right
4 while not valid():
5 remove(nums[l]) # shrink left
6 l += 1
7 best = max(best, r - l + 1) # window [l, r] is valid

Traps

  • Negative numbers break the 'shrink while sum too big' logic; use prefix sums + dict instead.
  • Update the answer at the right moment (after shrinking for 'longest').
  • Each index enters and leaves once → O(n), even with the inner while.

If you see… → do

“Longest substring / subarray such that …” (contiguous)

Expand r every step. While the window is invalid, shrink l. Record after shrinking.

“Shortest / minimum length subarray such that …”

Expand r. While the window is valid, record it, then shrink l.

The window rule depends on letter counts (covers t, at most k distinct, anagram)

Keep a count dict for the window. Track one number (missing, distinct, formed) so validity is O(1).

“Replace at most k characters to make them all the same”

Valid when window length − max frequency ≤ k.

“At most K distinct”, “at most K zeros”

Window with a count dict; shrink while the rule exceeds K.

“Exactly K distinct”, “exactly K odd numbers” (counting subarrays)

atMost(K) − atMost(K − 1). Count windows ending at r as r − l + 1.

Window size k is given (average, sum, max vowels in k)

Add nums[r], subtract nums[r − k]. Never recompute.

“Permutation of p inside s”, “all anagram start indexes”

Fixed window of size len(p) with letter counts; compare to p’s counts.

“Max (or min) of every window of size k”

Deque of indexes with decreasing values. Pop smaller from the back, pop expired from the front. Front is the max.

Subarray sum target, but the array has negative numbers

Not a window. Use prefix sums + a dict.

“Take k items from the two ends” (cards, operations to reduce x to zero)

Flip it: the items you don’t take form a contiguous middle window of size n − k.

Best single buy-then-sell, or “max later minus earlier”

Track the minimum so far; at each step compare today minus that minimum.

while (shrink) inside for (grow) over the same array

O(n): count that each index enters once and leaves at most once.

Space of a window solution

Size of the window’s bookkeeping: count map bounded by distinct values (O(26) for letters), a deque up to O(k).

Fixed-size window recomputed from scratch each step

Make it incremental: add the new element, remove the old one → O(n) instead of O(n·k).

DSA · 04

Stack

Open topic →

A stack holds the most recent unfinished thing; a monotonic stack holds items still waiting for their answer.

Must know

  • Matching pairs / nesting → push openers, pop on a closer and check it matches.
  • Evaluate / decode → push operands or (string, count) frames; pop when the scope closes.
  • Next greater / warmer → monotonic decreasing stack of indexes; a bigger value pops and answers them.
  • Previous smaller + next smaller → largest rectangle: each bar's width is between them.
  • Min stack → store (value, min so far) pairs.
  • Remove k digits / smallest result → monotonic increasing stack, pop while bigger and k > 0.
  • Circular array → loop 2n times with i % n.

Template

The template you'll own

1stack = [] # indexes still waiting
2for i, x in enumerate(nums):
3 while stack and nums[stack[-1]] < x:
4 j = stack.pop()
5 answer[j] = x # x is j's next greater
6 stack.append(i)

Traps

  • Store indexes, not values, when you need distances or widths.
  • Flush the stack at the end (sentinel 0 for histograms).
  • Empty-stack checks before pop / peek.

If you see… → do

Brackets, tags, nesting, “valid parentheses”

Push openers. On a closer, the top must be its partner; pop it. Valid if the stack ends empty.

Evaluate an expression (RPN, calculator, + − × with precedence)

Stack of numbers. RPN: operators pop two. Infix: push signed terms, apply × ÷ to the top immediately, sum at the end.

Nested repeats like 3[a2[c]], nested lists, mini-parsers

On “[” push (current text, count) and reset. On “]” pop and build prev + cur × count.

Backspace, undo, “..” in a path, cancel the last thing

A stack: push normal items, pop on the cancel action.

Stack that also returns min (or max) in O(1)

Store pairs (value, min so far) on every push.

“Next greater / warmer / higher element” for every position

Stack of indexes with decreasing values. When x beats the top, pop: x is that index’s answer.

“Previous smaller / greater element”, “span of days with price ≤ today”

Same scan. After popping everything that x beats, whatever remains on top is x’s previous greater (or smaller).

Largest rectangle in a histogram, max area under bars

Increasing stack of indexes plus a 0 sentinel. When popping bar j: width = i − new top − 1.

Next greater in a circular array

Loop i over 2n and use nums[i % n]; only push during the first pass.

“Remove k digits to make the smallest number”, smallest subsequence

Increasing stack: while k and top > current, pop. Trim leftovers from the end, strip leading zeros.

Things moving and colliding (asteroids, cancelling pairs)

Stack of survivors. A new left-mover fights the top right-movers until it dies or none are left.

Cars catching up and merging into fleets

Sort by position, closest to target first. Keep a stack of arrival times; a slower (larger) time starts a new fleet.

while stack and …: pop inside a for loop

O(n): every element is pushed once and popped at most once.

Space of a stack solution

Worst-case stack height: O(n) (sorted input never pops, or nested brackets).

For each element, scanning left or right for the first bigger/smaller one

That’s O(n²). A monotonic stack does it in O(n).

DSA · 05

Binary Search

Open topic →

Throw away half the search space each step. Works on any monotonic yes/no question, not just sorted arrays.

Must know

  • Template: find the first index where ok(mid) is true; lo, hi = 0, n; while lo < hi.
  • First / last position → two lower-bound searches (x and x + 1).
  • Rotated array → one half is always sorted; check if the target lies in it.
  • Minimum in rotated → compare mid with hi.
  • Binary search on the answer (Koko, ship packages, split array) → search the value; ok(v) is a greedy check.
  • 2D sorted matrix → treat as one array: r, c = divmod(mid, cols).
  • Peak element → move toward the bigger neighbour.

Template

The template you'll own

1lo, hi = 0, len(nums) # answer is in [lo, hi]
2while lo < hi:
3 mid = (lo + hi) // 2

“What’s the time complexity of this recursion?”

Ask three things: how many calls per call (on what size), how much work per call, then add the tree up level by level.

b recursive calls per call, each shrinking by 1

Tree has depth n and ~bⁿ boxes → O(bⁿ) × work per box.

One recursive call on half the input (binary search, fast pow)

log n levels × work per call → O(log n) if the work is O(1).

Two recursive calls on halves

O(n) work per call → every level costs n → O(n log n). O(1) work per call → leaves dominate → O(n).

Max depth of the call tree × frame size, plus memo tables, path lists and other extras. Not the total number of calls.

Memoized recursion or top-down DP

Time = distinct states × work per state. Space = states (cache) + depth (stack).

Heap

Open topic →

A heap gives you the smallest (or largest) item in O(log n), perfect for 'top k', 'next best' and merging sorted streams.

Must know

  • Python heapq is a min-heap; push negatives for a max-heap.
  • Top k largest → min-heap of size k; pop when it grows past k. O(n log k).
  • Kth largest in a stream → the same size-k min-heap; its top is the answer.
  • Merge k sorted → heap of the current head of each list.
  • Running median → max-heap for the low half, min-heap for the high half, sizes differ by ≤ 1.
  • Scheduling (tasks, rooms) → heap of end times / counts; greedily take the best available.
  • Heapify a list is O(n).

Template

The template you'll own

3heap = []

Traps

  • Tuples compare element by element: add an index to break ties between uncomparable items.
  • Size-k heap for 'k largest' is a min-heap.
  • Quickselect is average O(n) but worst O(n²).

If you see… → do

You need a max-heap in Python

heapq is min-only: push -x, read -heap[0].

You already have all the items up front

heapq.heapify(list) in O(n), not n pushes.

Push tuples (priority, tiebreak, payload). Use a counter or index as the tiebreak.

You need to delete or update an item that’s deep inside the heap

Lazy deletion: push the new version, and when an outdated entry reaches the top, skip it.

Min-heap of size k. Push, and pop when size > k. Root = kth largest.

Max-heap of size k (negate the key). Pop the farthest when size > k.

“Merge k sorted lists / arrays”, “smallest range covering k lists”

Heap of (value, which list, index). Pop the min, push that list’s next.

“Median of a data stream”, sliding median

Two heaps: max-heap for the lower half, min-heap for the upper. Keep sizes equal or lo one bigger.

Resources unlock over time and you always take the best available (IPO, meeting rooms, CPU tasks)

Sort by unlock time. Push newly available items into a heap keyed by “best”, pop when you act.

“Same item can’t repeat within n” (task scheduler, reorganize string)

Max-heap by remaining count. Take the most frequent; hold it out (a queue or a prev slot) until it’s allowed back.

Min-heap of (distance, node). Pop the closest, relax its edges, skip stale entries.

Building a heap from a full list

Best subsequence / subarray with a property (LIS, longest chain)

dp[i] = best that ends at i. Answer is max(dp).

Max product subarray (negatives flip signs)

Track both the max and the min ending here.

dp[i] = answer for the prefix of length i; try every last piece s[j:i].

Palindromic substrings / longest palindromic substring

Expand around every center (2n − 1 of them).

Two strings: common subsequence, edit distance, interleaving

dp[i][j] over prefixes, table (m + 1) × (n + 1). Compare the last characters.

Count paths or min cost in a grid moving right/down

dp[r][c] = combine(dp[r − 1][c], dp[r][c − 1]). First row and column are base cases.

Minimum edits (insert, delete, replace)

Match: diagonal. Else 1 + min(above = delete, left = insert, diagonal = replace).

0/1 knapsack in one row

Loop capacity backwards: for c in range(cap, w − 1, −1).

“Partition into equal sums”, “target sum with + and −”

Turn it into subset sum: boolean (or counting) 0/1 knapsack over sums.

One variable per state (holding, sold, resting) and transitions for each day.

Count states (table size), multiply by work per state (how many earlier cells one cell reads).

A 2-D table where row i only reads row i − 1 (or 1-D reading the last few)

Keep only the rows you need: O(m·n) → O(n), or O(n) → O(1).

Greedy & Intervals

Open topic →

Make the locally best choice when you can argue it never hurts. For intervals, sorting is the whole trick.

Must know

  • Max subarray → Kadane: cur = max(x, cur + x).
  • Reachability (jump game) → track the farthest reachable index.
  • Gas station → if total ≥ 0 an answer exists; restart after the tank goes negative.
  • Merge intervals → sort by start; extend the last or append.
  • Max non-overlapping / min removals / arrows → sort by end; keep the earliest-ending.
  • Meeting rooms → sort starts and ends (or a heap of end times).
  • Two-sided constraints (candy) → one pass left-to-right, one right-to-left.

Bit Manipulation

Open topic →

Numbers are columns of bits. XOR cancels pairs, AND masks, shifts move bits, and n & (n − 1) clears the lowest set bit.

Must know

  • x ^ x = 0, x ^ 0 = x → find the single number; missing number.
  • n & (n − 1) → drop the lowest 1 bit; power of two if result is 0.
  • n & −n → isolate the lowest 1 bit (split into two groups).
  • Test / set / clear bit i: n >> i & 1, n | 1 << i, n & ~(1 << i).
  • Subsets → masks 0..2ⁿ − 1.
  • Counting bits DP: bits[i] = bits[i >> 1] + (i & 1).
  • Add without +: XOR = sum without carry, AND << 1 = carry.

Java & OOP

Open topic →

Java variables hold references (arrows), interfaces are contracts, and the object's real class decides which override runs.

Must know

  • Four pillars: encapsulation (hide state), abstraction (expose a contract), inheritance (reuse is-a), polymorphism (one call, many behaviours).
  • Pass-by-value of references: a method can mutate the object, not reassign the caller's variable.
  • == vs equals: identity vs value. Override equals → override hashCode too.
  • Interface vs abstract class: capability contract vs shared half-built base (state + constructor).
  • Overloading picked at compile time; overriding picked at runtime by the object's class.
  • Generics: type safety at compile time; erased at runtime. ? extends read, ? super write (PECS).
  • Prefer HAS-A (composition) over IS-A unless it's truly a subtype.

“Explain the four pillars of OOP”

No. Always pass-by-value. For objects, the value copied is the reference, so a method can mutate the object but can’t repoint the caller’s variable.

Comparing objects, or using objects as HashMap keys

== compares references; equals() compares values. Override equals and hashCode together.

Choosing an access modifier

Start private. Widen only when needed: package-private → protected → public. Expose methods, not fields.

static, final, this

static = belongs to the class (one copy). final = assign once (variable), no override (method), no subclass (class). this = the current object.

Interface or abstract class?

Capability many unrelated classes share → interface. Shared state or a fixed algorithm across a family → abstract class.

Overriding vs overloading

Overriding: same signature in a subclass, chosen at runtime by the object. Overloading: same name, different parameters, chosen at compile time by declared types.

A collection or helper that should work for any type, safely

Generics <T>. Bound with T extends X when you need X’s methods. PECS: ? extends to read, ? super to write.

A fixed set of values (vehicle types, states, operations)

Enum with fields and methods, or constant-specific bodies. Use EnumMap for lookups.

Tempted to extend a class just to reuse code

Prefer composition (HAS-A) and delegate. Inherit only for a true IS-A that respects the parent’s contract.

“Is this a good design?”

Aim for low coupling (depend on interfaces, inject dependencies) and high cohesion (each class does one focused job).

SOLID is a list of smells and their cures; every design pattern is one of these cures applied to a specific change.

Must know

  • Single responsibility: one reason to change → split by who asks for changes.
  • Open/closed: add a new class instead of editing an if-else chain (Strategy).
  • Liskov: a subclass must keep the parent's promises (Square is not a Rectangle).
  • Interface segregation: small role interfaces, nobody implements dummy methods.
  • Dependency inversion: high-level code depends on interfaces; inject the implementation.

In code

The idea you'll own

1// D: depend on the interface, receive the implementation
2interface Notifier { void send(String to, String msg); }
3
4class OrderService {
5 private final Notifier notifier; // abstraction
6 OrderService(Notifier n) { this.notifier = n; } // injected
7 void place(Order o) { /* ... */ notifier.send(o.email(), "Placed"); }
8}
9// new OrderService(new EmailNotifier()) or new OrderService(new SmsNotifier())

Traps

  • Over-splitting into one-method classes for no change reason.
  • Throwing UnsupportedOperationException is an LSP/ISP smell.
  • DIP ≠ a DI framework; constructor injection is enough.

If you see… → do

A class that changes for unrelated reasons (maths, formatting, storage)

Split by reason to change: one class per actor who could request a change.

A 1,000-line Manager / Util / Service class

List its responsibilities, then extract each into a focused class the original delegates to.

“We’ll need to add more types later”

Put the varying behaviour behind an interface. New type = new class, no edits to existing code.

switch / if-else on a type field that keeps growing

Replace conditional with polymorphism: interface + one class per branch (Strategy).

A subclass that weakens the parent’s promise (throws, ignores input, changes meaning)

It isn’t a true IS-A. Use separate classes under a smaller shared interface.

An override that throws UnsupportedOperationException

Smell for LSP and ISP. Split the interface so the class never inherits that method.

An interface where implementers leave methods empty

Break it into small role interfaces; a class implements only the roles it plays.

Business logic depends on a concrete DB, API client or framework class

Define an interface on the business side; inject the implementation through the constructor.

new ConcreteThing() inside a service method

Move creation out: constructor injection, or a factory if creation depends on input.

Tempted to add an interface for every class “for SOLID”

Add abstraction where variation is real or likely (payments, storage, channels). Keep the rest concrete.

Creational Patterns

Open topic →

Creational patterns decide who creates objects, so callers don't depend on concrete classes or messy constructors.

Must know

  • Singleton: one instance. Thread-safe via eager init, holder idiom, enum, or double-checked locking with volatile.
  • Simple factory: one method picks the class from input.
  • Factory method: subclasses decide which product to create.
  • Abstract factory: a family of related products that must match (Mac button + Mac checkbox).
  • Builder: many optional params, readable and immutable result; validate in build().
  • Prototype: copy a configured object (deep vs shallow copy).

In code

The idea you'll own

1// Builder: named, validated, immutable
2Pizza p = Pizza.builder()
3 .size(Size.LARGE)
4 .cheese(true)
5 .topping("olives")
6 .build(); // validates once, returns an immutable Pizza

Traps

  • DCL without volatile can publish a half-built object.
  • Singletons hide dependencies and hurt testing: inject them.
  • Shallow copies share mutable fields.

If you see… → do

Exactly one instance per process (config, pool, registry)

Singleton, but prefer injecting that single instance over calling X.getInstance() everywhere.

“Write a thread-safe singleton”

Enum singleton (simplest, safe against reflection and serialization) or the holder idiom for lazy init. Mention DCL with volatile if asked.

Double-checked locking without volatile

Bug. Add volatile so the reference is published only after the constructor finishes.

Which class to create depends on input (a string, an enum, config)

Factory method of(type) returning the interface. Keep all the new calls in one place.

A base class runs a fixed algorithm but subclasses decide which object it uses

Factory Method: an abstract createX() the subclass overrides.

Several related objects that must match (theme, platform, region)

Abstract Factory: one interface with a create method per product; one implementation per family.

Constructor with many optional parameters, or several booleans in a row

Builder: fluent setters returning this, validate in build(), produce an immutable object.

Many similar objects that are expensive to set up

Prototype: configure one, then copy it (copy constructor or copy()).

Copying an object that holds lists, maps or other mutable objects

Deep copy the mutable parts (new list, new map, copied children). Prefer a copy constructor to clone().

Business code full of new ConcreteX()

Move creation to a factory or to the composition root and inject.

Structural Patterns

Open topic →

Structural patterns wrap or compose objects to add features, translate interfaces or hide complexity, without changing the original classes.

Must know

  • Decorator: same interface, wraps another, adds behaviour; stack in any combination.
  • Proxy: same interface, controls access (lazy load, cache, auth, remote).
  • Adapter: converts one interface into the one the client expects.
  • Facade: one simple entry point over a complex subsystem.
  • Composite: tree where leaf and group share an interface (files and folders).
  • Bridge: split two independent dimensions (shape × renderer) to avoid class explosion.
  • Flyweight: share immutable intrinsic state across many objects.

In code

The idea you'll own

1// Decorator: wrap, add, delegate
2Beverage order = new Whip(new Milk(new Espresso()));
3order.cost(); // 20 + 10 + 100 = 130
4order.description(); // "Espresso, milk, whip"

Traps

  • Decorator vs Proxy: same shape, different intent (add features vs control access).
  • Adapter changes the interface; Decorator keeps it.
  • Inheritance for every combination → class explosion.

If you see… → do

Add optional features in any combination, at runtime

Decorator: each feature wraps the same interface, delegates inward, then adds its part.

Control access to an object: lazy loading, caching, permissions, remote calls

Proxy: same interface as the real object, holds it, and decides when or whether to forward.

A third-party or legacy class has the wrong interface

Adapter: implement your interface, translate calls to theirs.

Clients must call many subsystems in the right order

Facade: one higher-level method that orchestrates them.

A tree where leaves and groups support the same operation (files/folders, menu/submenu, org chart)

Composite: common interface; the group implements it by looping over children.

Two independent dimensions of variation (shape × renderer, notification × channel)

Bridge: one hierarchy holds a reference to the other.

Huge numbers of objects that repeat the same heavy data

Flyweight: share immutable intrinsic state from a factory cache; pass extrinsic state per use.

Class names like MilkSugarWhipCoffee or RedCircleVector

Combination explosion. Use composition: Decorator for stackable add-ons, Bridge for two axes.

System design · 06

Behavioral Patterns

Open topic →

Behavioural patterns turn 'what varies at runtime' (the algorithm, the listeners, the action, the mode) into objects.

Must know

  • Strategy: swappable algorithm behind an interface.
  • Observer: subject keeps a list of listeners and notifies all on change.
  • Command: an action as an object → undo, queue, log, retry.
  • State: each mode is a class; the context delegates and switches state objects.
  • Chain of Responsibility: handlers in a line; each handles or passes on.
  • Template Method: fixed skeleton in the base class, steps overridden.
  • Iterator / Mediator / Memento: walk a collection / central coordinator / snapshot to restore.

In code

The idea you'll own

1// Strategy: the algorithm is an object you pass in
2interface FareStrategy { Money fare(Trip t); }
3
4class RideService {
5 private final FareStrategy pricing;
6 RideService(FareStrategy pricing) { this.pricing = pricing; }
7 Money quote(Trip t) { return pricing.fare(t); }
8}
9new RideService(new SurgeFare(1.8));
10new RideService(t -> Money.of(t.km() * 12)); // a lambda is a strategy too

Traps

  • Strategy vs State: who switches? Client picks a strategy; states switch themselves.
  • Observer memory leaks: unsubscribe.
  • Huge switch on mode → State.

If you see… → do

An if-else or switch choosing an algorithm (pricing, sorting, routing, compression)

Strategy: interface for the algorithm, one class (or lambda) per variant, injected.

“When X happens, notify A, B and C” (and more later)

Observer: listeners subscribe to the subject; the subject loops and calls them.

Undo/redo, queues of jobs, macros, audit log of actions

Command: wrap each action in an object with execute() (and undo()).

Traverse a custom collection without exposing its internals

Implement Iterable<T> and return an Iterator.

Behaviour depends on a mode, with rules about which mode comes next

State: one class per state; each method returns the next state; the context delegates.

A request must pass a sequence of checks, any of which may stop it

Chain of Responsibility: handlers linked with next; each processes or stops.

Several classes share the same algorithm skeleton but differ in a step

Template Method: final skeleton in an abstract class, abstract hook methods.

Many objects talking to each other directly (N×N links)

Mediator: they all talk to one hub that routes messages.

Save and restore an object’s state (undo, checkpoints) without exposing internals

Memento: the object creates an opaque snapshot and can restore from it; a caretaker stores them.

LLD Problems

Open topic →

One method for every machine-coding round: requirements → nouns → class diagram → patterns where things change → code → concurrency.

Must know

  • Clarify 3–5 use cases and what's out of scope.
  • Nouns → classes, verbs → methods on the class owning the data.
  • Enums for fixed categories; Strategy for rules that change (pricing, spot finding).
  • State for mode-driven machines (ATM, vending); Observer for displays/notifications.
  • Elevator: SCAN scheduling; requests as commands.
  • Booking: seat lock with expiry; avoid double booking by a conditional update or row lock.
  • Concurrency: check-then-act isn't atomic → synchronized / CAS / UPDATE … WHERE status='FREE' / optimistic version column.

In code

The idea you'll own

1// The LLD recipe, as code shape
2enum VehicleType { BIKE, CAR, TRUCK } // fixed categories -> enum

9}

Traps

  • God class with all the logic.
  • Forgetting two gates/users can race for one resource.
  • Not saying which pattern and why.

If you see… → do

Spend 3–5 minutes on scope: actors, 3–5 use cases, what’s out of scope. Write them down.

A list of use cases

Use an enum, optionally with fields and methods.

Chain of Responsibility from the largest note down; each takes amount / note notes and passes the remainder.

SCAN: keep direction, serve requests ahead in sorted order (TreeSet), reverse when none are ahead.

Model ShowSeat (seat × show) with status FREE/HELD/BOOKED and a hold expiry.

System Design Basics

Open topic →

Every HLD answer follows the same framework, and a few numbers let you size the system before drawing boxes.

Must know

  • Framework: requirements (functional + non-functional) → estimates → API → data model → high-level design → deep dives → trade-offs.
  • Numbers: 1 day ≈ 10⁵ s; 1M req/day ≈ 12 req/s; peak ≈ 2–3× average.
  • Scale out: stateless app servers behind a load balancer; state in DB/cache.
  • L4 vs L7 load balancing: by connection vs by request content.
  • API gateway: auth, rate limiting, routing in one place.
  • API design: resources, idempotency keys, pagination (cursor), versioning.
  • Real-time: short polling → long polling → SSE (server → client) → WebSockets (both ways).

In code

The idea you'll own

1// Estimation in five lines
2long dau = 100_000_000L, reqPerUser = 10;
3long perDay = dau * reqPerUser; // 1e9 requests/day
4long avgQps = perDay / 100_000; // 1 day ~ 1e5 s -> ~10k QPS
5long peakQps = avgQps * 3; // plan for peak -> ~30k QPS
6long storagePerYear = 5_000_000L * 1_000 * 365; // 5M writes/day x 1 KB -> ~1.8 TB/yr

Traps

  • Designing before agreeing on requirements and scale.
  • Single points of failure.
  • Forgetting read vs write ratio.

If you see… → do

“Design X” and a blank whiteboard

Requirements first: 3–4 core features, then scale, latency and consistency needs. Confirm before drawing.

Non-functional requirements

Ask: DAU and peak QPS, read/write ratio, latency target, availability vs strong consistency, data size and retention.

Need numbers fast

1 day ≈ 105 s. QPS = daily requests / 105, peak ×2–3. Storage = writes/day × size × 365 × years.

App servers must scale horizontally

Make them stateless: sessions in Redis or JWT, files in object storage, no local caches that must agree.

More than one app server, or a single point of failure

Put a load balancer in front with health checks; run at least two of everything.

Choosing a load-balancing algorithm

Round robin for uniform requests; least connections when request cost varies; consistent hashing when you need stickiness (caches, sockets).

Many microservices, each needing auth, rate limiting, logging

API gateway at the edge: authenticate, rate limit, route, add trace IDs.

Paginating a feed or a large, changing list

Cursor pagination: ?after=lastId&limit=20 with an index on the sort key.

A write that must not happen twice (payment, order) and clients that retry

Require an Idempotency-Key; store the result by key; return it on repeats.

REST vs gRPC vs GraphQL

REST for public CRUD, gRPC for internal low-latency calls (protobuf, HTTP/2, streaming), GraphQL for many clients needing different shapes.

Server must push updates to clients

Rare updates → polling. One-way stream → SSE. Two-way, low latency (chat, games, collaborative editing) → WebSocket.

WebSockets at millions of users

Dedicated connection servers + a registry (user → server) in Redis + pub/sub between servers; heartbeats; reconnect with resume.

System design · 09

Databases

Open topic →

Choose the store by access pattern, index for your queries, and know what transactions, replication and sharding cost you.

Must know

  • SQL: relations, joins, transactions. NoSQL: KV, document, wide-column, graph for scale/shape.
  • Index = sorted copy (B-tree) you can binary search; composite index follows the leftmost-prefix rule.
  • ACID; isolation levels: read committed, repeatable read, serializable. Lost update → row lock or version check.
  • Replication: leader-follower for reads; replication lag → read-your-writes issues.
  • Sharding: split by key; pick a key that spreads load and keeps queries on one shard.
  • Consistent hashing: adding a node moves only ~1/n of keys; virtual nodes even out load.
  • N+1 queries → join or batch fetch.

In code

The idea you'll own

1-- The three moves that fix most database problems
2CREATE INDEX idx_orders_user_time ON orders (user_id, created_at); -- fast reads
3
4BEGIN; -- safe writes
5UPDATE accounts SET balance = balance - 500 WHERE id = 1 AND balance >= 500;
6UPDATE accounts SET balance = balance + 500 WHERE id = 2;
7COMMIT;
8
9-- shard by user_id when one primary can't keep up -- scale writes

Traps

  • Sharding on a hot key (celebrity, today's date).
  • Index on every column slows writes.
  • Cross-shard joins and transactions are expensive.

If you see… → do

Not sure which database

Start with Postgres/MySQL. Move a specific workload to another store only when an access pattern or scale number demands it.

Massive write volume, simple key-based access, or flexible schema

Key-value (Redis/Dynamo) for lookups by key, Cassandra for append-heavy time-ordered data, Mongo for whole-document reads.

A hot read path that needs several joins

Denormalise: copy the few fields you need into the read model, update copies asynchronously.

Slow query filtering or sorting on a column

Add a B-tree index on that column; verify with EXPLAIN that the plan uses it.

Query filters on A and sorts or filters on B

Composite index (A, B), equality columns first, range/sort column last.

“This query is slow, what do you do?”

Run EXPLAIN ANALYZE: look for Seq Scan on big tables, bad row estimates, sorts and nested loops; then index, rewrite or cache.

Several writes that must all happen or none (transfer, order + payment record)

Wrap them in one transaction; guard invariants inside the UPDATE (WHERE balance >= ?).

Read a value in code, change it, write it back

Atomic UPDATE (SET x = x - ?), SELECT … FOR UPDATE, or a version column.

Read-heavy load on one database

Add read replicas; send reads there, writes to the primary; route a user’s reads to the primary just after they write.

Leaderless replication (Cassandra/Dynamo) with N copies

Choose W and R so that W + R > N for strong reads (e.g. N=3, W=2, R=2).

One primary can’t take the writes or hold the data

Shard by a high-cardinality key that keeps a request’s data together (user_id, tenant_id); avoid hot keys.

Mapping keys to a changing set of servers (caches, shards)

Consistent hashing with virtual nodes.

Caching, Queues & Resilience

Open topic →

Caches and queues buy speed and decoupling; sagas, outbox and breakers keep things correct and alive when parts fail.

Must know

  • Caching: cache-aside (most common), write-through, write-back; TTL + eviction (LRU).
  • CDN for static and media; object storage (S3) for files, DB for metadata.
  • Kafka: partitioned log; order within a partition; consumer groups; at-least-once → idempotent consumers.
  • Saga: a chain of local transactions with compensations instead of a distributed transaction.
  • Outbox: write the event in the same DB transaction, publish later.
  • Resilience: timeouts, retries with backoff + jitter, circuit breaker, bulkheads.
  • Toolbox: Bloom filter (maybe/no), geohash (nearby), HyperLogLog (approx count), JWT/OAuth.

In code

The idea you'll own

1// Cache-aside in four lines
2Product get(long id) {
3 Product p = cache.get("product:" + id);
4 if (p == null) { p = db.find(id); cache.set("product:" + id, p, Duration.ofMinutes(10)); }
5 return p;
6}

Traps

  • Cache stampede on a hot key expiring → lock or early refresh.
  • Retries without idempotency → double charges.
  • CAP: under a partition choose consistency or availability.

If you see… → do

Read-heavy data that tolerates seconds of staleness

Cache-aside: read cache → miss → DB → set with TTL.

Updating data that is cached

Write the DB, then delete the cache key (plus a TTL as a safety net).

A hot key expires and thousands of requests hit the DB at once

Lock/single-flight so one request reloads, others wait or serve stale; add TTL jitter; refresh hot keys early.

Images, videos, PDFs, uploads

Object storage (S3) with pre-signed upload/download URLs; store only the key and metadata in the DB.

Static assets or media served to users worldwide

Put a CDN in front with long cache headers and versioned file names.

Work that doesn’t need to finish before replying (email, thumbnails, reports), or spiky traffic

Put it on a queue; workers process at their own pace.

Events for the same entity must be processed in order

Use the entity ID as the Kafka message key so they share a partition.

Consuming from Kafka/SQS

Assume at-least-once delivery: make handlers idempotent (dedupe by event ID, upserts, conditional updates).

A business transaction spanning several services’ databases

Saga: sequence of local transactions with compensating actions on failure (orchestrated or choreographed).

Save to DB and publish an event, both must happen

Transactional outbox: event row in the same transaction; a relay/CDC publishes it.

Reads need very different shapes or scale than writes

CQRS: write model for commands, separate read models (built from events) for queries.

Consistency vs availability decision

Name it per feature: money, stock, uniqueness → CP. Feeds, likes, presence, carts → AP with eventual consistency.

Any remote call

Timeout + bounded retries with exponential backoff and jitter, only for idempotent operations.

A dependency failing or slow repeatedly

Circuit breaker (CLOSED → OPEN → HALF_OPEN) with a fallback; bulkhead its thread pool.

“Should we use microservices?”

Start with a modular monolith; split a service when a team, scaling need or deployment cadence demands it.

“Have we seen this before?” over a huge set, where a rare false yes is OK

Bloom filter in front of the real lookup.

Find nearby drivers, restaurants, stays

Geohash (prefix = area) or quadtree; query your cell plus 8 neighbours, then filter by exact distance. Redis GEO does this.

Count distinct users/IPs at huge scale

HyperLogLog (Redis PFADD/PFCOUNT).

Availability target

99.9% ≈ 8.8 h/yr down, 99.99% ≈ 53 min/yr. Serial deps multiply; redundancy in parallel adds nines.

Authenticating requests across many services

Short-lived signed JWT access token + refresh token; verify the signature locally; check roles for authorisation.

HLD Problems

Open topic →

Every classic is the same six moves; what differs is the one deep dive the interviewer cares about.

Must know

  • URL shortener: unique IDs (counter blocks + Base62), cache hot redirects, 302.
  • Rate limiter: token bucket / sliding window in Redis, atomic with Lua.
  • Feed: fan-out on write for normal users, on read for celebrities (hybrid).
  • Chat (WhatsApp): WebSocket gateways, message IDs, per-chat ordering, offline store + push.
  • Uber / Zomato: location updates into geohash cells, matching, state machine for orders.
  • YouTube / Dropbox: chunked upload to object storage, transcoding pipeline, CDN; dedup by chunk hash.
  • Airbnb / booking: availability search + strong consistency on reserve (conditional update).

In code

The idea you'll own

1// The deep dive of the URL shortener: unique 7-char codes
2// Each app server leases a block of 1,000 ids from a counter, then encodes locally
3String encode(long id) {
4 final String A = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
5 StringBuilder sb = new StringBuilder();
6 do { sb.append(A.charAt((int) (id % 62))); id /= 62; } while (id > 0);
7 return sb.reverse().toString(); // 62^7 = 3.5 trillion codes
8}

Traps

  • No numbers → no justification for caches or shards.
  • Forgetting failure modes and idempotency.
  • Over-designing before the interviewer picks a deep dive.

If you see… → do

Generate short unique IDs at scale (URL codes, order numbers)

Counter ranges leased per server + Base62 (or Snowflake IDs). Avoid hash-and-truncate.

301 or 302 for the redirect?

302 (temporary) if you want analytics on every click; 301 if you want browsers to cache and reduce load.

Rate limiter design

Token bucket per user/API key in Redis, atomic via Lua; return 429 with Retry-After; enforce at the gateway.

News feed / timeline

Hybrid: fan-out on write into per-user timeline caches; fan-out on read for celebrity accounts; merge at read.

Notification system

Accept → 202, dedupe by idempotency key, check preferences, queue per channel, workers with rate limits, retries and a dead-letter queue.

Autocomplete / typeahead

Precompute top-K completions per prefix offline from query logs (trie), serve from memory/Redis; debounce and cache on the client.

Chat app (WhatsApp)

WebSocket connection servers + presence registry (user → server) + pub/sub between servers + Cassandra for messages + push for offline users.

Ride matching / nearby search (Uber, Zomato)

Drivers stream locations into a geo index (Redis GEO / geohash / quadtree); query nearby; lock a driver while offering.

Video platform (YouTube)

Resumable upload to object storage → queue transcoding jobs into several bitrates → HLS/DASH segments on a CDN → adaptive bitrate playback.

Booking system (Airbnb, BookMyShow, hotels)

Availability row per resource per slot; atomic conditional update to HOLD all slots; confirm after payment; expire holds.

File sync (Dropbox, Drive)

Chunk files (~4 MB), address chunks by hash, upload only missing chunks, store metadata/versions separately, notify devices of changes.
