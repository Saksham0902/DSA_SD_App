    1

    The method

    One repeatable recipe for every machine-coding round. Every problem below is built with it, one step at a time, as a growing class diagram.

    Requirements → nouns → diagram → patterns → code

    1. Clarify (3–5 min). Actors, the 3–5 core use cases, what's out of scope. Write them down.
    2. Nouns become classes. Underline nouns in the use cases. Fixed categories (vehicle type, spot size) become enums.
    3. Draw the relationships. Who owns whom (◆ with multiplicity), who just knows whom (→). This is the class diagram from the Start page.
    4. Verbs become methods, on the class that owns the data: lot.park(vehicle), spot.tryOccupy(v).
    5. Ask what will change and put it behind an interface: pricing → Strategy, modes → State, reactions → Observer, checks → Chain.
    6. Concurrency and edge cases. Two users grabbing the same spot or seat? Full lot? Payment failure?
    2

    Parking Lot

    The most-asked LLD question, built from the requirements up.

    Think it through before drawing

    Use casesA vehicle enters and gets a ticket; it exits and pays. Several levels, several gates.
    Nounslot, level, spot, vehicle, ticket, gate; categories: vehicle type, spot size.
    What changes?How a spot is chosen; how the fee is computed. → two Strategies.
    What breaks?Two gates assigning the same spot at the same moment. → atomic claim.

    Now step through the diagram. Watch the requirement text: blue words are nouns (classes), amber words are verbs (methods).

    Watch it run

    The diagram is the design; this is the design in motion: cars arriving, spots being claimed, a fee computed on exit.

    3

    ATM & Elevator

    Two machines whose behaviour depends on their mode.

    ATM: a state machine with a cash chain

    Use casesInsert card, enter PIN, withdraw, get cash and the card back.
    What changes?What each button means depends on the step you're at → State. Which notes to dispense → Chain of Responsibility.
    What breaks?Two ATMs debiting one account at once → the bank does an atomic conditional debit.

    Elevator: SCAN, like a disk head

    Use casesHall buttons (up/down) on each floor, floor buttons inside each car.
    One carKeep moving in your direction while requests remain ahead (two sorted sets), then reverse.
    Many carsA dispatcher picks the car: nearest idle, or one already heading your way → Strategy.
    4

    Booking & races

    BookMyShow's model, and the concurrency bug hiding in every booking problem.

    BookMyShow: the seat is the hard part

    CatalogueMovie, Theatre → Screen → Seat. Rarely changes.
    The key insightA seat exists once, but it's free or taken per show. So you need ShowSeat (seat × show) with a status.
    What breaks?Two people click the same seat. → hold it atomically with an expiry while they pay, then confirm.

    Check-then-act is not atomic

    if (seat.isFree()) seat.book(user); reads, decides, then writes. Two threads can both read “free” before either writes, and both book. It's the same bug as the lazy Singleton race on the Creational page. Fixes, from one JVM to many servers: a lock; an atomic compare-and-set; a conditional UPDATE in the database.
